# 复用决策说明：minivLLM 是否可复用、为何不复用

> 决策日期：2026-06-07
> 前置报告：`reports/engine_inventory.md`（T2）、`learning/notes/01_老引擎结构审计.md`
> 本文定位：最终复用决策 + 隔离策略 + 对后续任务的具体建议
> 读者：T4（项目骨架）和 T11/T12/T16 的计划执行者

---

## 一、决策：选 C，新建 `diffusion_engine/`

**结论：C（完全不适合复用），新建 `diffusion_engine/`，逻辑隔离。**

这不是一个"倾向性"判断，而是一个基于 14 个模块逐一审计后的必然选择。minivLLM 的架构设计从根上服务于自回归语言模型推理，与扩散模型的 denoising-based 推理在三个维度上存在不可调和的结构性差异：

**1. 注意力范式不同。** minivLLM attention 使用 GQA + causal mask + RoPE，服务于"逐 token 可见历史"的约束。DiT/MMDiT 使用 full attention（所有 patches 互相 attend）+ AdaLN modulation，服务于"整张图并行去噪"的目标。这两套 attention 的 mask 结构、位置编码、注意力范围都是正交的。

**2. 迭代循环不同。** LLM 推理是自回归的，每次模型前向只输出一个新 token，并追加到已有序列中。扩散推理是迭代去噪，每次模型前向输出的是"从当前噪声到干净数据的矢量场"，中间 latent 在每步去噪后全部刷新。前者依赖 KV cache 来避免重算，后者不需要也不受益于 KV cache。

**3. 条件注入不同。** LLM 的 transformer block 使用静态 RMSNorm。DiT 的 transformer block 使用 AdaLN-Zero：timestep embedding 和文本条件 dynamic 生成 scale/shift 参数注入到每个 block 的归一化层。整个 conditioning 机制在旧引擎中不存在。

这三个差异不是"实现细节不同"，它们决定了模型 forward 的基本结构。改造 minivLLM 的成本大于从零写，因为你需要先理解旧代码的 LLM 专用逻辑，再删除，再重写。而新写一个针对扩散设计的 transformer block，代码量不会超过 100 行。

## 二、次选 B 的边界，什么情况下 B 才可接受

B（部分复用）指的是"核心 transformer 组件可复用，diffusion 专用模块新写"。在本项目语境中，B 的含义需要被严格限定：

**B 绝对不意味着：**
- 从 `Qwen3Attn` 出发"改一改"得到 DiT attention
- 把 `Qwen3DecoderLayer` 当成 DiT block 的基类
- 保留 `KVCache` 并"适配到扩散"

**B 唯一可接受的含义：**
- 复制 `SiluAndMul` 到新引擎（11 行代码）
- 读旧代码的 `Attn` 类作为 PyTorch attention 的手写模板参考（不复制，仅参考写法）
- 参考 `RMSNorm` 的 residual 融合接口设计模式，迁移到 AdaLN 的 `forward(x, residual)` 接口
- 参考 `Qwen3DecoderLayer` 的 Pre-Norm + 显式 residual 传递结构，迁移到 DiT block 的骨架
- 参考 `RotaryEmbedding` 的 cos/sin 预计算缓存 + `@torch.compile` 模式（内容完全不同）

**B 可以接受的前提条件（同时满足）：**

1. minivLLM 同时也是 DiT 推理引擎（但目前它不是，且永远不会是）
2. 本项目极简到只需 attention/linear 风格参考（本项目目标 include 完整 DiT/MMDiT 实现，不满足）
3. 开发者非常熟悉旧引擎代码，改动成本低于重写（对于本项目，理解旧代码的 LLM 专用逻辑带来的认知负担大于新写）

当前项目不满足这三个前提中的任何一个。因此 B 在本项目语境中降级为"仅复用 SiluAndMul + 代码风格参考"，不构成对 C 的实质替代。

## 三、隔离策略

以 C 为主决策后，三层面的隔离策略确保新旧引擎不会互相污染：

### 3.1 物理隔离：目录层面

```
diffusion/
├── minivLLM/          # 只读，不修改，仅审计和风格参考
├── diffusion_engine/  # ★ 新建，所有新代码在此
│   ├── __init__.py
│   ├── layers/
│   │   ├── attention.py     # 从头写的 full attention（非 GQA，无 causal mask）
│   │   ├── activation.py    # 复制 SiluAndMul（唯一直接复用）
│   │   ├── norm.py          # AdaLN-Zero 实现
│   │   ├── linear.py        # Linear wrapper（参考旧风格，独立实现）
│   │   └── pos_embed.py     # 2D sinusoidal position embedding
│   ├── model/
│   │   ├── dit.py           # DiT 主实现
│   │   ├── mmdit.py         # MMDiT 实现（joint attention）
│   │   └── components.py    # timestep embedding, patch embedding 等
│   ├── scheduler/
│   │   └── noise_scheduler.py  # DDPM/DDIM/Flow Matching
│   └── utils/
│       └── config.py           # diffusion 专用配置
├── learning/
│   └── notes/                # 中文学习笔记
├── docs/
│   └── *.html                # 中文静态文档
└── reports/                  # 周报和审计报告
```

**关键约束：**
- `minivLLM/` 目录内不创建任何新文件
- `minivLLM/` 目录内不修改任何已有文件
- `diffusion_engine/` 不 import 任何 `minivLLM/` 下的模块（除显式复制 `SiluAndMul` 的 11 行代码）
- 如需参考旧引擎代码风格，在注释中标注来源但不建立运行时依赖

### 3.2 依赖隔离：虚拟环境层面

- `minivLLM/pyproject.toml` 声明的 Python 3.13 + torch 2.11+ 环境**仅供 minivLLM 使用**
- `diffusion_engine/` 的依赖通过 `diffusion/pyproject.toml`（顶层）声明，使用**独立的虚拟环境**
- 两个项目使用各自的 `uv.lock`，避免依赖版本冲突
- 扩散项目可能需要额外的依赖（`diffusers`、`transformers` 用于 CLIP/T5 编码器、`imageio` 用于输出保存），这些不会也无需安装到 minivLLM 的环境中

### 3.3 概念隔离：可借鉴的 LLM 概念 vs 不能套用的 LLM 概念

| 概念 | 可在扩散中借鉴 | 不可套用 | 原因 |
|------|-------------|---------|------|
| **Transformer block 骨架** | Pre-Norm 结构、显式 residual 传递 | RMSNorm、causal attention | 扩散需要 AdaLN + full attention |
| **Attention 核心公式** | Q·K^T/√d_k → softmax → matmul V | GQA、causal mask、RoPE | 扩散无 GQA 优化需求，无因果约束 |
| **Normalization** | residual 融合的 API 设计模式 | RMSNorm 的具体实现 | 扩散需要 AdaLN/GroupNorm |
| **Position encoding** | 预计算缓存的工程模式 | RoPE 旋转逻辑 | 扩散使用 2D sinusoidal embedding |
| **SwiGLU activation** | silu(x) * y 的精确公式 | FFN 的 gate_up/gate_down 结构 | 扩散 FFN 需要 AdaLN conditioning |
| **缓存策略** | `register_buffer` + `@torch.compile` 的优化模式 | KV cache 语义 | 扩散不需要 KV 缓存，可考虑 latent buffer 复用 |
| **自回归解码** | 无 | 逐 token 生成逻辑 | 扩散是并行去噪，非自回归 |
| **Prefill/Decode 两阶段** | 无 | 分阶段推理设计 | 扩散是一致的前向 pass |

## 四、对后续关键任务的具体建议

### 4.1 T11（DiT 实现）

**不要从 `minivLLM Attention` 改造。** 从零写 `diffusion_engine/layers/attention.py`。你要写的 attention 是：
- Full attention（无 causal mask），所有 patches 互相 attend
- 无 GQA（num_heads = num_kv_heads，或不区分 K/V heads）
- 无 RoPE（位置信息来自 patch embedding 的 2D sinusoidal 编码）
- 可选支持 text-image cross-attention（如果实现 MMDiT 的 joint attention）

写这套 attention 的代码量不会超过从 `Qwen3Attn` 中删除 GQA + causal mask + RoPE 并重写的量。直接手写 PyTorch 的 Q·K^T → scale → softmax → matmul V 流程更干净，也更能保证你对每行代码的理解。

**唯一可抄的**：`SiluAndMul` 的 11 行代码可以直接复制到 `diffusion_engine/layers/activation.py`。

### 4.2 T12（CFG 采样）

**采样循环从零写，不要参考 `validate_model.py` 的 greedy loop。** 你的采样循环是一个 `for t in reversed(scheduler.timesteps)` 的迭代：
1. 构建 conditional 和 unconditional 两个 batch（或使用 batched CFG）
2. 对两个 batch 分别调用 DiT 前向
3. 在 vector field 层面做 CFG 融合：v_cfg = v_uncond + cfg_scale * (v_cond - v_uncond)
4. 用 scheduler 执行一步去噪更新

LLM 的 greedy decoding（`last_logits.argmax(dim=-1)` → 追加到序列 → 重新构建 input）在结构和语义上与扩散采样循环毫无关系。

### 4.3 T16（系统优化）

**主优化方向不是 KV cache。** 扩散推理的系统优化焦点应该是：
- **Activation checkpointing**：在显存受限环境下，对 DiT block 做 gradient checkpointing 式的前向内存释放
- **CFG batched forward**：将 conditional 和 unconditional 的 forward 合并到一个 batch 中，避免两次独立前向
- **Latent buffer 管理**：在去噪循环中复用 latent buffer 避免不必要的内存分配
- **VAE 解码优化**：如果内存允许，批量解码多步结果（如在 CFG 采样中积累多张图后一起 VAE decode）
- **torch.compile**：对 DiT 的 attention 和 FFN 做 `@torch.compile` 加速（参考 `rope.py` 的编译模式）

这些优化策略与 LLM 推理的 KV cache 优化（page attention、prefix caching、continuous batching）是正交的。

## 五、决策总结

| 维度 | 决策 |
|------|------|
| **复用等级** | C（完全不适合复用） |
| **次选** | B（仅复用 SiluAndMul + 代码风格参考） |
| **唯一直接复用的代码** | `activation.py` 的 `SiluAndMul`（11 行） |
| **物理隔离** | `diffusion_engine/` 新目录，不修改 `minivLLM/` |
| **依赖隔离** | 顶层 `pyproject.toml` 独立虚拟环境 |
| **概念隔离** | 参考 Pre-Norm 结构 / residual 接口 / SwiGLU activation / 编译缓存模式；不可用 GQA / causal mask / KV cache / RoPE / RMSNorm |
| **T11 建议** | DiT attention 从零写，不要从 minivLLM Attention 改造 |
| **T12 建议** | 采样循环从零写，不要参考 LLM greedy decoding |
| **T16 建议** | 主优化方向是 activation checkpointing + CFG batched forward + `torch.compile`，不是 KV cache |
